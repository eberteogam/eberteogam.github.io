Orchard Core in a Nutshell

  • Front end is .liquid or .cshtml; the back end is .NET Core.
  • Plugins (extensions) live in Admin > Configuration > Features. If a feature is called OrchardCore.*, it's built into OC. Lombiq (Hungary-based) focuses on extensions.
  • A tenant is an isolated site within Orchard Core — each with its own database, users, themes, modules, configuration, and content.
  • NuGet packages are declared in .csproj — the equivalent of build.gradle / pom.xml.
  • Ports are set in LaunchSettings.json; leave default ports for web dev.
  • Orchard historically used NHibernate; today it's YesSql.
  • When developing an Orchard Core feature you're building a module (class library), not a standalone application — dotnet run will produce "The current OutputType is 'Library'". That's expected; use dotnet build.

Configuration & the Tenant Lifecycle

  • The root appsettings.json and appsettings.Development.json are standard .NET Core — app-wide defaults and initial setup. App_Data/Sites/Default/appsettings.json is Orchard-specific and loaded per tenant; the per-tenant file always wins over root settings.
  • OrchardCore_AutoSetup is only used the first time a tenant is created (or if it doesn't exist yet). Once the tenant exists, only the files in its own folder control its DB/provider — not auto-setup or global settings. However, if the tenant file exists but misses needed objects, it falls back to the root appsettings*.json for those objects.
  • SQLite: an empty connection string means Orchard Core auto-creates a local database file. MySQL: an empty connection string fails setup — you must create the database yourself and provide connection details.
  • In the root development settings, the Tenants array points at which recipe will run.

Recipes vs Migrations

  • The theme's Setup recipe (Themes/…/Recipes/*.recipe.json) is where the site's packages are assembled — think of it as tables and seeds in one file:
    • steps: [{ "enable": … }] — migrations, data seeds, table creation (think Laravel's migrations)
    • steps: [{ "Values": … }] — content items, initial data inserted into the migrated tables (think Laravel's seeders)
  • Typical features a setup recipe enables: OrchardCore.Admin (dashboard), OrchardCore.Deployment (import/export UI), OrchardCore.Contents, OrchardCore.Recipes, OrchardCore.ContentTypes, OrchardCore.ContentFields, OrchardCore.Menu, OrchardCore.Taxonomies, OrchardCore.Alias, OrchardCore.Autoroute.
  • Modules define their tables and columns through YesSql in C#-based migrations (src/Modules/…/Migrations.cs).

YesSql — a Document Store on a Relational DB

  • Strictly a .NET library, written in C# — not compatible with other frameworks. It's the exception among ORMs: a document-database style on top of a relational DB, similar to Marten.
  • It maps your getters/setters as a MapIndex that goes onto a document-model DB in object format. The Document table is always present — it's how documents are stored as JSON — in both standalone YesSql and Orchard Core.
  • Querying flow: set an index, then query the index — never the raw object. The provider does the mapping. LINQ and indexing are the main query paths.
  • Since data is stored as JSON, if I need to query by an attribute I have to create a new index table indexing that attribute.
  • YesSql by itself doesn't support C#-based migrations — it auto-creates tables from registered documents and indexes. Inside Orchard Core, C#-based migrations exist via DataMigration classes and SchemaBuilder — that's Orchard's own system layered on top.
  • ORM equivalents: EF Core (.NET) ⇔ Eloquent (Laravel) ⇔ Hibernate/JPA (Spring Boot). YesSql sits apart, as does Marten.

The Database Layer

  • The tenant's DB name lives in App_Data/Sites/Default/appsettings.json; all views are in the DB; log events are documents.
  • ContentItemIndex maps to the Content Items module; the Document table depends on it — it holds the complete page as JSON, which gets rendered.
  • SQL Server LocalDB quick facts: main files are .mdf / .ldf; instance (localdb)\MSSQLLocalDB; files under %LOCALAPPDATA%\Microsoft\Microsoft SQL Server Local DB\Instances\MSSQLLocalDB; trusted connection string: Server=(localdb)\MSSQLLocalDB;Database=Devdb;Trusted_Connection=True;
  • Document-oriented DB models (SQL or NoSQL) center on a main Document table using JSON or XML, and can also store media assets. Key-value models (e.g. Redis) store data as unique key/value pairs.

dotnet CLI Survival Kit

  • dotnet build — builds without opening listening ports; checks errors and produces artifacts. Accepts .sln and .csproj.
  • dotnet run --project src/…/file.csproj — always builds first, restores NuGet packages, and opens ports. Works only on .csproj, never .sln. Add --no-build to skip the build and just open ports.
  • dotnet clean — deletes bin and obj (all build cache). ≈ mvn clean.
  • dotnet restore — downloads NuGet dependencies declared in .csproj.
  • dotnet publish — compiles the whole project into a folder with the .dll (compiled app), .deps.json, and .runtimeconfig.json.
  • dotnet watch — hot reload: applies code changes (method bodies, Razor, static files) without restarting the process; bigger changes trigger an automatic rebuild. Different from both run --no-build and build.
  • dotnet pack --configuration Release creates a NuGet package; consume with dotnet add package <Name>.
  • Terminology: an artifact is the build output (.dll) that gets stored and deployed. A solution (.sln) just tells the IDE/MSBuild which projects are included, their dependencies, and build configurations — it can contain many projects, while a .csproj defines exactly one.

Diagnosing builds

  • --verbosity detailed prints errors and messages while the build runs; append > build.log 2>&1 to export to a file.
  • dotnet build …csproj -bl:msbuild.binlog creates a structured log for deep inspection — open it with MSBuild Structured Log Viewer (use build, not run). Or just dotnet build /bl.
  • dotnet list package --include-transitive — visualize every package and transitive dependency of a csproj.
  • dotnet nuget list source — shows the source order used; regardless of declared order, the SDK always checks the local cache first (%USERPROFILE%\.nuget\packages). Whichever source serves a package — nuget.org or an offline feed — it ends up in that global cache, along with all transitive dependencies.
  • dotnet package search <Name> --source https://api.nuget.org/v3/index.json --take 10
  • Logging convention: Console.WriteLine($"My Var is: {nameVari}").
  • Clean, disposable build environment with Docker: docker run --rm -it -v "$PWD":/src -w /src mcr.microsoft.com/dotnet/sdk:9.0 bash

MSBuild .props / .targets & the Node Pipeline

  • A NuGet package can ship build/ folders that MSBuild auto-imports into consuming projects: the .props file is imported early and only declares properties — the binding between local file paths and what will be run — while the .targets file holds the executable <Target>/<Exec>/<MSBuild> actions in the package's build tree.
  • That's how Node/corepack/pnpm run inside a .NET build: neither Node nor npm/pnpm is invoked by Orchard Core itself — they're triggered by the Lombiq NodeJS Extensions package, whose .targets hook into the build lifecycle and execute the front-asset pipeline (asset copying → JavaScript → Markdown → styles) for every class library that has a package.json following the Node convention. A project without package.json is skipped — no pnpm build.

Kestrel vs IIS

  • Kestrel is the default server for .NET Core; it appears in Task Manager as dotnet.exe. IIS Express shows as iisexpress.exe.
  • web.config is only an IIS configuration file. Kestrel configuration must be done in C# (Program.cs) — you cannot put Kestrel config in web.config, nor IIS config in Program.cs.
  • HttpContext.RequestAborted is signaled by Kestrel when the client disconnects. A cancellationToken handles server-side cancellation of HTTP requests — the equivalent of AbortController/AbortSignal around fetch() in JS.

Routing, Controllers & DI Conventions

  • URL routing: {ModuleName}/(Admin if declared)/{controllerName}/{functionName}/{id?}
  • Naming: constructor parameter mediaAuditService (camelCase) · private field _mediaAuditService (underscore + camelCase) · interface IMediaAuditService (PascalCase with I prefix).
  • Declaring controllers: admin page → [Admin]; front end → [Area("YourModule")]; APIs → [Route(…)] or [ApiController] + [Area] + [Route("")], with [HttpGet/Post(…)] on actions.
  • The service pattern: Controller → depends on a service interface (the contract — the list of method signatures the service class exposes). The service class implements it and injects ISession or IContentManager (for higher-level ops) in its constructor — business logic + data-access queries in one place.
  • DI flavors: constructor injection, setter injection, method/parameter injection, property injection.
  • Task<T> is an async wrapper — the equivalent of Promise<T>.

Spring Boot ↔ .NET Translations

  • DI registrations in Program.cs/Startup.cs (services.AddScoped<IMyService, MyService>()) ≈ Spring Boot bean configuration (@Service + @Autowired).
  • private final MyService service (Java) ⇔ private readonly IMediaAuditService mediaAuditService (C#).
  • NuGet packages in .csproj ≈ Maven/Gradle dependencies in pom.xml/build.gradle.
  • dotnet clean ≈ mvn clean.
  • Recipes ≈ Laravel migrations + seeders (see above); EF Core ⇔ Eloquent ⇔ Hibernate/JPA.

LINQ

  • Prefer the lambda default methods — GroupBy, Max, Average, Where, OrderBy, Select, Distinct — for massive objects, not hand-rolled higher-order functions. Pagination: Skip(#).Take(#).
  • LINQ also has a query syntax, but stick with the default methods. It's a query language over ORM providers — the methods and syntax both compile down to the provider.

Debugging Deployment Imports & OpenAPI

  • "Unexpected error occurred while importing the deployment package" — the detailed error is in the back log. The usual three culprits: a rendering error due to a broken URL, a duplicate alias or object, or a JSON key expected at the end of an object.
  • OpenAPI: .NET has an OOB swagger/v1/swagger.json route available — just add in Program.cs/Startup.cs: 
    app.UseSwaggerUI(options =>
{
    options.SwaggerEndpoint("/swagger/v1/swagger.json", "API V1");
});
