Docker Layer Mechanics

  • Each Dockerfile line (FROM, RUN, COPY, ENV, …) is a cache layer, rebuilt when that instruction's inputs change. When one layer changes, it executes itself and invalidates everything after it — no more cache from that point on.
  • Inspect layers on Windows with docker history (or watch the cache during the build); on Linux (Docker Engine) they live under /var/lib/docker/overlay2/.
  • Windows 11 requires WSL2 — a docker command actually runs inside WSL2 as Linux.
  • Docker disables apt cache files to save space during layer builds (apt-config dump | grep Dir::C shows pkgcache/srcpkgcache empty — not normal in an LXD container). To re-enable, comment out everything in /etc/apt/apt.conf.d/docker-clean and apt update.
  • Chain of artifacts: a Dockerfile builds into an image (-t imageName:Tag); an image is run into a container (takes --privileged, port mappings -p, -d for background); a container is started with start; its internal terminal is accessed with exec.

Docker CLI Patterns

  • docker exec -it <container> bash — open a shell in a living container (on Linux this makes bash PID 1's child rather than systemd).
  • docker run --rm -it <img> bash — interact with an image live: --rm deletes the temp container on exit; -it gives you the interactive shell; -v "$PWD":/src -w /src mounts the local directory into the container.
  • Disposable .NET build environment: docker run --rm -it -v "$PWD":/src -w /src mcr.microsoft.com/dotnet/sdk:9.0 bash
  • Cache cleanup: docker buildx prune (nicer interface) or docker builder prune (legacy).
  • docker build -t image -f dockerfile — build defaults to a file named Dockerfile; use -f otherwise.
  • run is for temporary environments — it knows nothing about port mappings, volumes, or env vars unless you explicitly add them, and its listening IP is randomized inside the engine unless -p is specified. Compose services use their declared internal IPs/ports.
  • Docker volumes on Windows live at \\wsl$\docker-desktop\mnt\docker-desktop-disk\data\docker\volumes.

Compose & Dockerfile Structure

  • Conventions: docker compose up looks for compose.yaml by default (old default docker-compose.yml); use -f for custom names. In the compose file, a service's build: . looks for the Dockerfile. Mental model: Dockerfile → image; compose → build/run process.
  • compose.override.yaml for local development is best practice.
  • docker compose -f x.yml run --rm <service> gives a temporary container; up creates containers, down deletes them; -d runs in background.
  • Volume keys: left side binds to the local host, right side to the container. If no volume is declared, a new volume exists only inside the container — not on the host.
  • Dockerfile vocabulary: FROM = base image; WORKDIR = mkdir + cd in the container's filesystem; ENTRYPOINT = what runs at start. Stages: build (heavy tools — SDK, Node, compilers) → publish → runtime (only what's needed to run; lighter). Multiple build/runtime stages are allowed. Best practice: CMD ["my-service", "server"].
  • Image references: sdk:9.0 → .NET SDK; aspnet:9.0 → ASP.NET runtime.

systemd in Containers (and Podman)

  • Best practice is not having systemd in a Docker container — that's why it doesn't come OOB. If you need it: pull an image containing systemd, run with cgroups configured, or use Podman.
  • To make systemd PID 1 in Docker: the Dockerfile needs CMD ["/lib/systemd/systemd"]; docker exec without -it bash so PID 1 comes from the image; and run with --privileged or you'll hit cgroup/mount issues.
  • Podman exposes systemd mode explicitly (--systemd=true|false), whereas Docker has no such option — cgroups must be set up and systemd installed manually.
  • systemd controls all units: .service, .socket, .timer, .mount, .target. There are cgroups v1 and v2.
  • Portainer password reset: stop the Portainer container → docker pull portainer/helper-reset-password → docker run --rm -v portainer_data:/data portainer/helper-reset-password → start it again.

WSL2

  • Control Panel > Programs > Turn Windows features on/off: WSL and Virtual Machine Platform must be enabled — required for distro installation (not for the wsl2 engine itself).
  • %USERPROFILE%\.wslconfig = independent Linux configuration (RAM, processors). Docker Desktop's Settings > Resources > Advanced limits derive from and match it.
  • Sizing intuition: more RAM, fewer cores = plenty of desk space but not enough hands to work quickly; less RAM, more cores = many workers with nowhere to put tasks.

Unix Diagnostics

  • PIDs live in /proc; see what a PID is executing with cat /proc/<PID>/comm.
  • Swap size: swapon --show. Memory usage: top.
  • Ports: install net-tools, then netstat -tulpen.
  • Processes: install procps for ps (the Unix equivalent of PowerShell's Get-Process) — ps aux | grep 'name'.

Terminals

  • Windows PowerShell — object-oriented, functions, integrates with .NET, COM objects, APIs. cmd.exe — plain text. Linux — Bash.
  • rm -rf = recursive + force. $Env:PATH merges system and user environment variables.
  • ZoomIt when presenting.

Git Team Workflow

  • git fetch — what's new on the remote, without applying it. git status — commits ahead/behind and changed files. git pull — apply all remote changes locally.
  • Pulling a big commit while preserving local edits: stash (without committing), pull, then pop the stash.
  • Exporting changes between repositories: create a patch in the source repo and apply it in the target.
  • Branch flow: dev branch (has fixes) → staging branch (production/main); every deploy is a hotfix (green canary deployment). Branch naming convention: feature/issue/task . feature_name.
  • Deployment slots: a staging slot with its staging DB and a production slot with its production DB, exchanged with a swap.
  • GitHub Actions: a step is either uses (a reusable piece) or run (a shell command). Permissions can apply to all jobs in a workflow file or to one specific job.

Odds & Ends

  • CKAN vs Snowflake: CKAN (open-source open-data portal platform used by governments) stores a CSV and lets you search by title/tags/description — but can't query the contents; Snowflake loads the CSV into a table and runs SQL on it. One is a library catalog, the other a research database.
  • Graphviz: digraph = arrow edges, graph = plain lines; rankdir (TB/LR/BT/RL) is root-level only — inside a subgraph it's ignored; [dir=back] points an arrow against the root level; containers must be named starting with cluster_.
  • "Lift & Shift": putting everything inside a VM/instance without using managed services.
  • VCF (VMware Cloud Foundation): full-stack private cloud built around Day-0/1/2/3 operations, using vRA (Infrastructure-as-Code + governance policies).
  • Secret management (HashiCorp Vault): secret rotation and audit trail.
