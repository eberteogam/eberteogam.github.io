Installation (Tomcat + MySQL)

  • Everything in SailPoint is an object: IIQ represents most platform entities as object types, each implemented as a Java class (WEB-INF\classes\sailpoint\object).
  • WEB-INF\classes\iiq.properties holds the properties for all databases; WEB-INF\bin> iiq console connects.
  • First schema run (create_identityiq_tables.mysql) creates three databases: identityiq, identityiqah, identityiqplugin.
  • Environment: set JAVA_HOME, CATALINA_HOME, JRE_HOME; start MySQL (net start MySQL80 / MySQL84), connect with mysql -u root -p -h 127.0.0.1 -P 3306, then Tomcat's startup.bat.
  • Linux flow: drop the .war in /webapps (Tomcat auto-extracts; otherwise jar -xvf), optionally extend attributes in IdentityExtended.hbm.xml, chmod +x iiq then ./iiq schema (generates the DB scripts for MySQL/PostgreSQL/Oracle), source the SQL, configure iiq.properties, then ./iiq console → import init.xml (default system objects; init-lcm.xml optional). Patching: update the war, source upgrade_identityiq_tables.mysql, ./iiq patch x.xpx, run Tomcat.
  • Version bookkeeping lives in spt_database_version (and spt_hist_database_version on the ah schema) — system and schema versions must match the patch level.
  • Beanshell documentation ships with the instance: …/identityiq/doc/Javadoc/index.html.

Core Concepts

  • Identity Cube — the employee object (UI: Attributes; identities are added via Lifecycle Manager).
  • Authoritative app — only identity-related data (the trusted source of people). Non-authoritative apps — access-related data, drivers, roles, others.
  • Aggregation — create an app, link it to the third-party system, then run an aggregation task; SailPoint pulls the data in for mapping in the Manager Correlation module. Correlation Manager is similar to setting foreign keys (e.g. Manager ↔ EmployeeID).
  • Entitlements — the actual actions a user is authorized to do in other apps; stored in the Entitlement Catalog.
  • Orphan account — an identity in a third-party app that isn't part of the HR employee source. Manual correlation is the process of resolving an orphan account to an identity. A merged identity with multiple app access reads like: Bob, Smith, "Accounts Payable, Accounting, Payroll".
  • Refresh is done in ID Mapping / updateExistingId; run tasks from Setup > Tasks; chain them with the Sequential Task Launcher.
  • Business need map: Access Certification, Access Request (entitlement or role = collection of entitlements), Automated Provisioning, Password Management (AD), Policy Management (rules & regulations). The business model behind it: Policy Model, Role Model, Workflow Engine, Identity Warehouse (repository), Reports, Risk Model (confidence level 0–1000).
  • Provisioning — access allocation and revocation, creating entities and entitlements — acts on objects in response to events.

Onboarding Applications

  • Authoritative app from CSV: Application Definition with AppType DelimitedFile → aggregation task → ID mapping per attribute.
  • Non-authoritative apps: set connector type → account schema → account correlation (mapping between the authoritative data and the app's attributes) → rules (correlation & customization). Orphan accounts get discovered here.
  • JDBC connector (e.g. MySQL): getObjectSQL is the equivalent of a DTO; the JDBC connector ships four OOTB rules. Server-based connectors (LDAP, AD) have no rules — their schemas are preconfigured.
  • LDAP connector: single domain. Vocabulary: cn common name, dn distinguished name, dc domain component, ou organizational unit, sn surname. LDAP is the protocol; slapd is the server. AD connector: supports multiple domains.
  • Apps can also be onboarded/merged via XML — one app, several rules, and aggregation tasks combined in one import (Settings > Import from file); a SQL join across databases can feed a single app.
  • Multiple-owner apps: define a workgroup so several users hold the owner entitlement. Groups/populations are identity sets by criteria (advanced analytics filters), used mainly for advanced certifications.
  • Reset options while practicing: delete identities and managed attributes, or Tasks > Prune Identity Cubes; wipeout = drop the DB and regenerate the schema.

Policies

  • A policy is a violation trigger on entitlements/activity; run it via tasks. The policy owner is notified and takes action; violations can be allowed or revoked. Policies can be attached to certifications and reports.
  • Types: Activity (audit account behavior, e.g. logins per day), Account (one account per app — a second one triggers it), Risk (score threshold), Advanced (e.g. no login for 190 days).
  • Naming collision to keep straight: a "policy" in SailPoint is a triggered violation; in ServiceNow a UI Policy is just front-end behavior.

Certifications

  • A certification is the automated periodic review of policies, set up as a campaign (Setup > Certifications). A certification contains multiple identities; each identity has multiple items to approve/revoke.
  • Types: Identity certifications (targeting particular identities) and event-driven certifications (location/department/region change, new onboarding — rule-based).
  • States to know: policy decisions are Allow/Revoke; Open = pending access review; access decisions are Approve/Revoke; Complete = every action taken. Completed means all story tasks done — sign-off requires everything clear.
  • An optional challenge period: when a revoke is contested, you cannot sign off the certification until it's resolved.
  • Best practice: set up an electronic signature (Global Settings) to sign off certifications.
  • Completion happens in My Work > Access Reviews; monitor via Setup > Certifications, Intelligence > Advanced Analytics (type: AccessReview), and Intelligence > Reports.

Risk Model

  • Optional topic — many orgs cover it via third parties. Identities > Identity Risk Model and Applications > Application Risk Model.
  • Flags trusted identities/applications by security threat on a 0–1000 score: Low < Medium < High risk profiles. Score varies with the target and source system access. Threats are declared role-access-based or entitlement-based; overall scores under Intelligence. Default report templates exist.

Roles

  • A role is an object encapsulating sets of access — a collection of entitlements (think AD roles). Four types: Organizational (container), Business (assigned — the UI display, e.g. "Dev"), IT (detected — stores the entitlements, e.g. AWS), Entitlement.
  • Flow: Business Role — required/permitted → IT Roles → Entitlements. Inherited roles create parent/child structures.
  • Ways to define roles: manual; Business Role Mining (creates roles from existing data); IT Role Mining (attribute-based, e.g. Region); Entitlement Analysis (checkout-style: add apps to a cart); XML (Debug page, search "bundle" — roles are exportable as XML); API/rule.
  • Role Mining with ordered identity attributes creates one role per attribute value, with an optional name prefix (e.g. prefix Demo + attribute Origin → Demo.America, Demo.Asia, Demo.Europe). Every mined role must be enabled; create IT roles from Role Mining Results > Task Results.
  • To apply roles to identities, run the task "Refresh assigned, detected roles and promote additional entitlements."
  • Provisioning Policy — the form generated when a role is requested (Lifecycle Manager), the rough equivalent of a ServiceNow UI Policy.

Rules & Beanshell

  • Rules are where Beanshell customization lives; getters/setters are defined in the Rule Registry. Prefer getEmail()-style getters; use getAttribute("email") when the key isn't defined.
  • Key rule types: BuildMapRule (map two identities into one application before aggregating), PreIterateRule (runs before aggregation — e.g. convert XML to CSV), PostIterateRule (after — e.g. send a completion notification), MapToResourceObjectRule (modifies the Identity Cube).
  • In business processes there are scripts and rules — a script is defined once and not reused; a rule is reusable.
  • Rule source is wrapped as <Source><![CDATA[ … ]]> in the XML.

Debugging & Operations Tools

  • iiq console / SDK: connectorDebug <App> iterate (accounts or groups), count/list identity|application|bundle (bundle = roles), import path/rule.xml, delete by sysID.
  • JConsole (Java console, OOB) to monitor health; the Administrator Console manages tasks on deployment (PIDs) and provisioning.
  • Syslogs: Global Settings > IIQ Configuration > Miscellaneous. Audits: Global Settings > Audit Config + Intelligence > Advanced Analytics.
  • Log4j: uncomment the class to enable, e.g. log4j.logger.sailpoint.api.Aggregator=debug.
  • Reports live under Intelligence > Reports (OOB templates included); reports and tasks are stored as TaskDefinition objects (XML) — view/modify raw queries from the Debug pages.
  • Real orgs keep all IIQ objects in Git; the build process pushes through a QA pipeline.

Lifecycle Manager & Workflows

  • Lifecycle Manager authorizes access and profile creation when new identities appear. Its components import via init-lcm.xml, then patch the instance.
  • Lifecycle events: Joiner, Mover, Leaver — each has a business process (workflow), e.g. create/close tickets in an ITSM system as part of the logic. Certifications trigger on joiner and mover, not leaver.
  • Provisioning policies (Lifecycle Manager > Identity Provisioning Policies) drive custom validation forms; Manage User Access adds/removes entitlement access; password synchronization (Login Configuration) authenticates multiple systems with one password.
  • SSD (Services Standard Deployment) encompasses: Services Standard Build (SSB), Framework (SSF), Performance (SSP), Test (SST), and the IIQ Testing Framework (ITF).
