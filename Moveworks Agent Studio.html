Moveworks Agent Studio

Working notes on building AI service agents — plugins, conversational processes, compound actions, DSL, and knowledge ingestion.

What Moveworks Is

Employee support automation. Its configuration language is called DSL (roughly the equivalent of Laravel's Eloquent in spirit: a compact, declarative layer over the underlying engine). Agents feed from knowledge bases, SharePoint, and the internet.

Architecture

Plugin (natural language trigger) → Conversational Process (function calling to the LLM) → Compound Action (request orchestrator) → HTTP Action (single request). Data Types are rich business objects used to manipulate things like Jira/GitHub/VTB issues.

  • Plugin — its description is used by the Reasoning Engine to decide when to trigger it. It must be rich in keywords and context, since the description is what differentiates one plugin from another when a user prompts. Natural-language triggers define pass and reject steps; Launch Rules scope the audience.
  • Conversational Process — always starts with activities. Activities (API requests) → Slots (temporary data containers) → Decision Policies (if-then business logic in DSL, roughly the equivalent of a Switch in a Compound Action). In Input Mapping there is a system_prompt key used to log with your user prompt response. Ctrl+Shift+V validates when the Validate option isn't shown.
  • Compound Action — always starts with steps; the API orchestrator. Custom scripts are written in APIthon (a subset of Python).
  • HTTP Action — a single request. Reusable HTTP Connectors serve multiple HTTP Actions — the equivalent of ServiceNow's REST API Explorer module.
  • Content Activity — the user-experience side: return information as Knowledge, a Form, or plain text.
  • Built-in actions — OOTB methods usable in the Conversational Process, e.g. mw.get_user_by_email, mw_send_plaintext_chat_notification.

Description fields: for HTTP Actions, Compound Actions, and Conversational Processes the description is primarily internal. Only the plugin description drives the Reasoning Engine's trigger decision.

Slots & Resolvers

  • A slot is a data placeholder — like a declared global variable (not local, not environment). Slot validation has two parts: the Validation Policy (the DSL condition on the slot value) and the Slot Validation Description (the error description the agent returns).
  • Static resolver — must be declared in the Input Mapping of the conversational process step.
  • Dynamic resolver — no Input Mapping declaration needed. Use for multiple applications at once, ambiguous requests, and context analysis.
  • Data Types — Schema: create a data schema matching your request's JSON response using the "Import JSON" option with one object. Resolver: create a method and map it to an existing HTTP Action.
  • Platform data prefixes — meta_info.user.email_addr takes the value from the user who triggered the flow; data.user_email takes it from Input Args. Mapping slots use data.<slot_name>.

Memory & Context

  • The result JSON from a Compound Action's Test run is what gets passed to the LLM's function calling — Moveworks calls this the LLM's memory (Semantic Working Memory). It holds roughly ~7,000 tokens of active conversation context.
  • That context persists as long as the user stays in the same chat session asking relevant follow-ups. Changing topic entirely or starting a new session clears the working memory for the new topic.
  • Conversation context (the reasoner's session memory across turns) auto-clears every 24 hours, and is what copilot clearhistory flushes.
  • The Data Bank is different: a per-execution scratch space created and destroyed within a single plugin run — it lives for milliseconds to seconds, nothing to do with the 24 hours.

Moveworks DSL

  • String: $LOWERCASE, $TRIM, $REPLACE…
  • Time: $TIME, $PARSE_TIME, $FORMAT_TIME, $ADD_DATE (adds time to a date)…
  • Types: $TEXT, $INTEGER, LENGTH…
  • Collections: $FILTER, and in the Data Mapper: MAP, SORT, COALESCE, FILTER.
  • MWDSL is strictly typed — even if an array contains a single element, the system still sees it as a List, not an Object.
  • DSL and mappers execute faster than APIthon at the execution level; prefer them where possible.
  • Great debugging tool: the DSL and Mapper Playground.

Development Workflow

  • Publish order matters when working a complete flow, otherwise you get access denied: HTTP Actions → Compound Action → Conversational Process.
  • Troubleshooting — the Logs app. Filter logs by plugin (Root UUID) or by requestor.
  • Marketplace plugin states — Install: fully packaged agent, deploy immediately. Build: a design template plus integration guide; you create the plugin in Agent Studio yourself. Get Notified: no installable template released yet; register interest.
  • When installing internal plugins you can customize the plugin's workflow to your needs in Agent Studio.

Knowledge Ingestion

  • Pipeline 1 — Classic ingestion, internal knowledge: the connector catalogs each site's pages, then fetches each page and indexes its metadata (JSON-wrapped HTML). The bot can answer page-level questions and hand out links; deeper document crawling is configured separately.
  • Pipeline 2 — Classic ingestion, files: the same connector family (ms_graph) aimed at document libraries — catalogs the files, extracts docx/PDF/pptx contents, and indexes them. This is the pipeline that answers from inside documents.

Adoption Ideas

  • Different welcome messages per department.
  • License-renewal reminders (user answers yes/no, then analytics on the numbers), outage-report reminders, new-hire campaigns.
  • Calendar Campaigns to visualize all reminders in one place.
  • Channel usage goes through approvals — therefore roles must exist.
  • The key: make it a daily assistant. Certification focus: Agent Studio.
