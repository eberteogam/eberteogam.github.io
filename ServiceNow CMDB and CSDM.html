ServiceNow CMDB & CSDM v5

Implementation notes — the Ingest → Govern → Insight pipeline, IRE rules, CMDB Health, and the CSDM domain model.

CMDB in One Paragraph

The CMDB is a data repository following Ingest → Govern (Lifecycle) → Insight. If I could summarize it in two things: control the budget department through Normalization, and automate as much of the data flow into the CMDB as possible. It underpins Service Management, Asset Management, Operations Management, Cloud Operations, Compliance, and Application Portfolio Management. Ultimately you want to make business decisions — and you cannot make good business decisions on bad data.

Core Concepts

  • Asset — part of the financial lifecycle; has financial value. Created during procurement, or when Discovery first inserts a CI into the CMDB (its asset record gets created). It can have two different CIs during lifecycle management.
  • Configuration Item (CI) — part of technical operations; tracked for service delivery. Created during procurement or through a discovery tool. Tangible (hardware) or intangible (software). A CI is something you want to monitor, manage, measure, and track.
  • Attributes — info that further describes the CI: serial number, OS, etc. Prefer the base system attributes given in each class — don't create custom attributes.
  • CI Class — a table describing a specific type or group of CIs with common attributes. Hierarchy sample: Hardware > Computer > Server > Nginx. If a base system class exists, extend it instead of copying it. The "CMDB CI Class Models" plugin enables a range of additional classes.
  • CI Reclassification — migrating a CI from one cmdb table to another due to upgrade / downgrade / switch.
  • Non-discoverable attributes — Support group, approval group, managed-by group. Managed By Group = the specific group responsible for an entire CI class (unless configured to be managed by a contractor).
  • Foundational tables — core data shared across multiple tables (users, groups, locations).
  • Snapshots are available on the CMDB to track a CI record. To prevent inserts from an unwanted data source, create an IRE Data Source Rule (cmdb_ire_data_source_rule).
  • Non-CMDB tables usable with IRE (per glide.identification_engine.non_cmdb_tables): Location cmn_location, Department cmn_department, Cost Center cmn_cost_center, Building cmn_building, User sys_user, Group sys_user_group. These six are the only ones — and their identification rules are set directly on their table list view, not through CI Class Manager.
  • Housekeeping: archive CIs at 90 days and delete at 3 years to reduce cost and keep organized.

CMDB Table Conventions

  • Business Service data — cmdb_ci_service_business
  • Service data — lifecycle management cmdb_ci_service & technology offering service_offering
  • Router data — cmdb_ci_router · Servers — cmdb_ci_server · CI relationships — cmdb_rel_ci
  • App scope & host — cmdb_ci_business_app, cmdb_ci_appl, cmdb_ci_service_discovered, via ITOM (Service Mapping and Discovery)

The CMDB Pipeline

1. Data Source (Discovery, Service Graph Connector, Import Set, …)

If running Discovery on a Linux instance, make sure the SSH user on that host has the right file permissions.

2. ETL — non-Discovery / external sources (optional)

System Import Sets → Robust Import Set Transformers (RTE), or Transform Maps. External-to-internal field mapping itself is done in Transform Maps, Service Graph ETL, or integration mappings.

3. IRE — Identification & Reconciliation Engine (two steps)

Identification runs first, then reconciliation. Identification is about inserting/updating a CI; reconciliation is about which source may update it. To test rules, use background scripts.

  • Identification rules (declared in CI Class Manager) — decide if a payload matches an existing CI or creates a new one, using criteria that identify unique CIs. Match found → existing CI updated; no match → new CI record. This is the duplicate-prevention layer. Good practice: identify an application by its installation directory or configuration file path, which stays unique per instance even on the same host. glide.identification_engine.enable_identifier_optional_condition = true adds an advanced optional filter on identifier entries.
  • Reconciliation rules — decide which source can overwrite which attributes.
    • Static — Data Refresh Rules: how and when data refreshes; if a higher-priority source hasn't updated within the interval, lower-priority sources are allowed to update.
    • Dynamic: optional, only with Multisource CMDB enabled; focused on multisource across Discovery sources. Rules on a specific class take precedence over parent-class rules, and dynamic rules take precedence over static ones when both exist for the same attribute.
    • Data source precedence completes the picture.
4. CMDB tables

Where the (still messy) CIs land.

5. Normalization

Standardizes software and hardware, consumed by SAM and HAM — enables compliance and audits. Normalization in CMDB is different from ETL: it's the concept of consolidating all available versions. Mapping flow for hardware: CMDB → Discovery → HAM → SAM.

Ingestion Methods

  • ServiceNow Discovery (horizontal / agentless): Router → Switch → DB → App. Schedule-based, so not real-time.
  • Service Mapping (top-down / tag-based / ML-powered): maps services to their IT component relationships (e.g. Order_API → Tomcat → RabbitMQ → Oracle). Focus on CI hierarchy — it pays off in outage reports.
  • Agent Client Collector (ACC, agent-based): an agent per host; collects CPU, memory, software versions, usage, OS settings, patch level, real-time performance, processes. Use this for true real-time discovery.
  • Import Sets + Transform Maps: do not bypass the IRE — that produces duplicate CIs. First set identifier/reconciliation for the table in cmdb_identifier; then add an onBefore script in the transform map that calls the CMDBTransformUtil API so imported data goes through the IRE.
  • IntegrationHub ETL: OOTB guided UX that already runs IRE within the ETL.
  • Service Graph Connectors: detailed ingestion from multi-resource filters; unique SGC records should be identified during coalesce or IRE.
  • Patterns plugin: Discovery and Service Mapping Patterns — an OOTB library to populate CIs and relationships.
  • Multisource CMDB: requires the ITOM Discovery plugin and glide.identification_engine.multisource_enabled = true.
  • Limiting discovery at the beginning (e.g. by IP ranges) helps create a solid base and prevents data overload.

Non-Discoverable Group Data

For Managed-by Group, Support Group, and Change Group there are two options; both synchronize group attributes across all CIs of the class. Audit periodically with Data Manager afterwards. Group information is critical when incidents are raised against CIs.

Option 1 — CI Class Manager

Set the group attributes at the class level.

Option 2 — Technology Management Offering (takes precedence over Option 1 if both are set)

Using forms:

  1. Create a CMDB Group — Configuration > CMDB Groups (cmdb_group)
  2. Create a Dynamic CI Group — automates CI inclusion by criteria (cmdb_ci_query_based_service)
  3. Create a Technology Management Service (cmdb_ci_service_technical)
  4. Create a Technology Management Offering (service_offering) — defines the conditions and the responsible groups
  5. Associate the Dynamic CI Group to the offering as a relationship
  6. Set the group attribute
  7. Verify the sync business rule: "CSDM - Sync Group Attributes" (check support_group, assignment_group, managed_by_group in the script)
  8. View CIs with the synced group attribute

Using Service Builder: the same flow as a guided, step-by-step wizard — define the technical service, its offering, responsible groups, associate the Dynamic CI Group, review and submit.

Governance

Multisource ingestion tracking
  • cmdb_multisource_data tracks all CI records and attribute history, including data sources. Common attributes live in columns; all attributes live in a JSON blob.
  • Part of the ITOM Discovery license; accessible from a CI record's Related Links or from CI Class Manager's Reconciliation Rule tab.
CMDB Health Dashboard — the three C's

A scoreboard covering Completeness, Compliance, and Correctness, populated by scheduled jobs; points at non-compliant CIs. First define inclusion rules: which CI classes fall under which metric — focus only on the classes your organization actually handles ("is a" maps an entire hierarchy).

  • Completeness — is non-discoverable data populated? Start with Recommended fields (Assigned To, Location, Support Group, Change Group, Managed By, Serial Number, Name); Required examples: Serial Number, Name, MAC. Activate in three spots: class attributes (column label + mandatory), the class Health → Completeness filter, and the Health Dashboard scheduled jobs.
  • Compliance — does CI data pass audits? Activate via the Certification Filter, Certification Template, and Audit tabs, plus the Compliance scheduled job.
  • Correctness — is the data legit? Duplicate (more than one entry for one real CI), Orphan (condition-based CIs with no server relationship — only one orphan rule per class), Stale (forgotten/outdated; you set the timestamp threshold).
  • CMDB Group Health Dashboard — CI collections scored on the same metrics, shown in the CMDB Workspace.
Duplicate remediation
  1. Duplicate CI Remediation Wizard — friendly UI ("Remediate" button) to merge duplicates into one. OOTB.
  2. De-Duplication Templates — bulk resolution, pre-configured rules and criteria, schedulable.

Two properties worth setting when defining IRE: glide.identification_engine.skip_duplicates and …skip_duplicates.threshold.

Reclassification
  • Happens automatically during Discovery, or manually. Controlled by glide.class.upgrade.enabled (e.g. Server → Windows Server), glide.class.downgrade.enabled (Windows Server → Server), and glide.class.switch.enabled (Linux Server → Windows Server). In these flows the CI record itself isn't changed — a CI reclassification task is created.
  • Reclassification Restriction Rules — a more granular, newer mechanism that takes precedence over the legacy glide.class.*.enabled properties: the IRE applies attribute updates from the incoming payload but skips the class change entirely; no reclassification task is created. The CI keeps its sys_class_name, everything else in the payload lands.
Data Manager (CMDB Workspace)

A policy-driven framework for bulk CI management: Retire, Archive, Delete, Delete CMDB Related Entry (end-of-life policies), Attestation (similar to certification campaigns in IGA tools), and Certification.

CSDM v5

On the CSDM diagram: a solid line is a relationship record (cmdb_rel_ci); a dashed line is a reference field (a column on one record pointing to another). There's no single way to implement CSDM — the path depends on your focus:

  • Step-wise: Foundation → Crawl → …
  • Domain-centric: one domain at a time (left-to-right, right-to-left, or middle-out)
  • Outcome-centric: start from the burning problem and work backwards
Domains and their tables
  • Foundation — referential data on a CI. Product/Model (cmdb_model and its many child model tables: application, software, hardware, service, contract, facility, consumable, firmware, AI system/content…), Product Feature (sn_dpr_model_product_feature), SBOM (sn_sbom_doc), Business Process (cmdb_ci_business_process), Contract (ast_contract), Location (cmn_location), CMDB Group (cmdb_group), Group/Team/User (sys_user_group, sys_user), Life Cycle (life_cycle_stage, life_cycle_stage_status), Company/BU/Department (core_company, business_unit, cmn_department), Knowledge (kb_knowledge). Lifecycle = stage + stage status together, for both the operational side of a CI and the physical asset until end-of-life.
  • Ideation & Strategy (outside the CMDB) — Product Idea (sn_align_core_product_idea), Planning Item (sn_align_core_planning_item). Where the idea starts; enough ideas to take business decisions. Foundation object living here: cmn_value_stream.
  • Design & Planning — Business Capability (cmdb_ci_business_capability, what your company does), Business Application (cmdb_ci_business_app, the wrapper for all hardware and software of an app — the highest application record), Information Object (cmdb_ci_information_object, what type of information lives inside each app — customer data ⇒ PII audits, credit-card data ⇒ PCI audits).
  • Build & Integration (optional) — SDLC Component (cmdb_ci_sdlc_component); the DevOps Change Data Model is a data model/app spanning multiple sn_devops_* tables. Think microservices and CI/CD — the things you deploy.
  • Service Delivery — Technology Management Service (cmdb_ci_service_technical), Technology Management Offering (service_offering), Service Instance (cmdb_ci_service_auto, the application service per environment, with child tables cmdb_ci_service_discovered, …_by_tags, …_calculated, cmdb_ci_query_based_service), Dynamic CI Group (cmdb_ci_query_based_service), Application (cmdb_ci_appl — Nginx, MySQL, Tomcat). The operational piece: which people/groups deliver the technical steps.
  • Service Consumption — Business Service (cmdb_ci_service_business), Business Offering (service_offering), and the catalogs (not CMDB CI tables): Service Catalog (sc_catalog, sc_category, sc_cat_item, sc_request, sc_req_item, sc_task), Product Catalog (pc_product_cat_item ↔ cmdb_model), Sales Catalog (an sc_catalog record). Identify the business consumers; impacts from Service Delivery populate here.
  • Portfolios — Enterprise/Service (DPM), Personal (DPM), Application (EA), Project (SPM), Technology (EA). SPM portfolio lenses: Value Stream, Product, Organization, Goals, Project Portfolio/Program, Strategic Investments.
Terminology that trips people up (IPC = Incident, Problem, Change)
  • Application (cmdb_ci_appl) — operational CI, used in IPC. DB servers, Java, Tomcat, httpd.
  • Business Application (cmdb_ci_business_app) — not operational, not used in IPC, not version-specific. A listing of apps for EA/portfolio purposes: knowing what exists in the organization.
  • Application Service (cmdb_ci_service_auto) — operational, used in IPC. Uniquely identifies each environment and who uses it.
  • Business Service (cmdb_ci_service) — operational, used in IPC. The consumers and what's impacted: internal (accounting, HR capabilities) or external (what money is made from).
  • Technology Management Service (cmdb_ci_service_technical) — operational, used in IPC. Who is responsible for the technology, very granular (app layer, DB layer, server layer) — the Support Group.
Foundational-data lab walkthrough (CD-* convention)
  1. Analyze the CSDM Data Foundations Dashboard (plugin: com.snc.cmdb.csdm.activation).
  2. Create foundational data — groups (CD-Support Group, CD-Change Group) and locations (CD-Parent/Child Location).
  3. Business Application (CD-Business Application: define app, architecture type, owner) — remember it's not an operational CI and is never used in INC/PRB/CHG, and it's not version-specific.
  4. Business Capability (CD-Capability, related to the Business Application via Provided By::Provides) and Information Object (CD-Information Object, Uses::Used by).
  5. Business Service + Offering via Service Portfolio Management > Service Builder — a business service is made of one or more offerings; set lifecycle Phase: Catalog / Status: Operational, with Support and Change groups on the offering.
  6. Technology Management Service + Offering — same lifecycle pattern, groups on the offering.
  7. Create a Service Instance and configure the relationships between services, offerings, and business applications.

KPIs in the CMDB Context

A KPI is a measurable value used to judge performance — the meaning is constant, the subject changes per module. In CMDB Health, KPIs measure data quality (the three C's). In SLA/OLA they measure service performance against time or responsibility commitments (SLA breached/met, time to respond/resolve, % resolved within target). Related vocabulary: SLA = customer-facing; OLA = internal between teams; SLI = the metric you measure; SLO = the target for an SLI over time.
